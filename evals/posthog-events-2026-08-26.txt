--------------------------------------------------------------------------
HOW THE PAYLOADS WERE READ
--------------------------------------------------------------------------
The browser devtools bridge shows the CORS preflight but not POST bodies, and
posthog-js binds its transport and its logger at init - before any patch
injected from outside the page can reach either. Two attempts at reading the
payload in-page (wrapping fetch/sendBeacon/XHR; wrapping console.log) both
recorded NOTHING for exactly that reason, and are noted here so the next person
does not repeat them.

What worked: evals/posthog_capture_proxy.mjs, a pass-through that sits in the
path, logs the decoded payload, FORWARDS to https://us.i.posthog.com and
returns the real upstream status. So the lines below are a real click, the real
payload, and PostHog's real answer. During the run only
NEXT_PUBLIC_POSTHOG_HOST in site/.env.local pointed at the proxy; it has been
put back to https://us.i.posthog.com (verified after the run).

Interactions were real mouse clicks and real typing in Chrome, not scripted
dispatch. `citation_expand` was additionally confirmed against posthog-js's own
debug logger (?__posthog_debug=true), which printed:
    [13:30:45] [PostHog.js] send "citation_expand" Object
    [13:30:49] [PostHog.js] Bad HTTP status: 401 API key is not valid: personal_api_key

--------------------------------------------------------------------------
THE 401 - WHAT POSTHOG ACTUALLY SAID
--------------------------------------------------------------------------
Not an inference from the key's shape. PostHog's ingestion named it:

    HTTP 401  API key is not valid: personal_api_key

and its flags endpoint separately returned:

    {"type":"authentication_error","code":"authentication_failed",
     "detail":"The provided API key is invalid or has expired."}

The value in NEXT_PUBLIC_POSTHOG_KEY is a PostHog PERSONAL API key. Client-side
ingestion needs the PROJECT API key (Project Settings), which is a different
credential.

SECURITY, and this is the part that matters more than the broken events: a
personal API key is an ACCOUNT-SCOPED SECRET, and it is sitting behind a
NEXT_PUBLIC_ name. Next inlines NEXT_PUBLIC_* into the browser bundle. Had this
been set in Vercel and deployed, that key would have been served to every
visitor in readable JavaScript. It has not been deployed - it exists only in
the local .env files, both gitignored - but it should be REVOKED in PostHog
rather than merely swapped out, because it has been on disk in a file destined
for a client bundle.
